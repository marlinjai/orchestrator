**NEW REQUIREMENT — Medusa-style configurable backorder (Marlin 2026-06-27, see `docs/research/2026-06-27-medusa-inventory-backorder-reference.md`).** Overselling is NOT a hard error; it is per-variant configurable via the `manage_inventory` + `allow_backorder` flags CM-08a added to `product_variant` (`manage_inventory` default true, `allow_backorder` default false). The new Kysely reserve MUST branch 3 ways per line (resolve the variant's flags FIRST, from `product_variant` via the variant id / sku the line carries):
- **Case A, `manage_inventory = false` (untracked):** return `{ ok:true }` immediately with NO inventory_level access and NO reservation/movement row. Untracked variants may have NO inventory_item / inventory_level row at all, so you MUST resolve the flag from `product_variant` BEFORE touching inventory_level. Always sellable.
- **Case B, `manage_inventory = true && allow_backorder = true` (backorder):** reserve ALWAYS succeeds: the guarded UPDATE drops its availability predicate (`SET reserved_quantity = reserved_quantity + needed ... WHERE item/loc` with NO `(stocked - reserved) >= needed` clause), so `reserved` may exceed `stocked` and `available_quantity` goes NEGATIVE (= backorder depth). Still write the reservation + stock_movement rows; still idempotent on request_id. Never returns a shortage.
- **Case C, `manage_inventory = true && allow_backorder = false` (managed):** the EXISTING guarded decrement, UNCHANGED — `... WHERE (stocked_quantity - reserved_quantity) >= needed`; 0 matched rows -> `{ ok:false, shortages }`. Because CM-08a DROPPED the DB `CHECK (reserved <= stocked)`, this WHERE clause is now the SOLE oversell guard for managed items, and it is atomic (the row lock serializes concurrent reservers). This is the case the concurrency test pins.
The kit path applies the same per-component branch (a kit can mix tracked, untracked, and backorder components). The 3 cases share the READ COMMITTED tx, the idempotency pre-checks, the 23505 re-detection, and the ascending kit lock-ordering.

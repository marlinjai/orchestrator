## Definition of done

- New `src/server/commerce/provisioning/provision.ts`:
  - `provisionCommerceTenant(opts: { tenantGroupId: string; slug: string; connectionString?: string }): Promise<{ schema: string; applied: string[] }>` that opens a direct postgres.js OWNER connection (default `COMMERCE_OWNER_DATABASE_URL`, `max:1`, `prepare:false`), calls `provisionTenant(owner, { tenantGroupId, slug, appRole: 'commerce_app', tenantMigrations: COMMERCE_TENANT_MIGRATIONS })`, closes in `finally`, returns the result. Reads the URL at call time (not import). Throws a clear error if `COMMERCE_OWNER_DATABASE_URL` is unset, naming it as the OWNER role.
  - `migrateAllCommerceTenants(opts?): Promise<MigrateAllResult>` wrapping `migrateAllTenants(owner, { tenantMigrations: COMMERCE_TENANT_MIGRATIONS, batchSize?, onSchemaDone? })` on the same owner connection, for shipping new commerce DDL across the fleet.

If framer-clone does NOT own tenant-group creation (ids come from auth-brain), wire provisioning at the first framer-clone touchpoint that has a tenantGroupId AND owns DDL (e.g. the project/site create path), and make it idempotent (re-provision is a safe no-op per the runner). Provisioning runs on the OWNER connection out-of-band from the request's app-role pool; do NOT provision on the `commerce_app` base handle (it has no DDL privilege). If the cleanest hook is async/deferred, surface that; do not block a user request on a long DDL run if the codebase has a job/outbox seam, but do NOT invent new infrastructure: prefer the simplest correct wiring and FLAG any deferral.

Then `migrateAllCommerceTenants` over a fleet of >=2 provisioned tenant-groups applies cleanly and is resumable (re-run applies nothing new).
